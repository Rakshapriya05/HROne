# REVIEW.md

Defects found in the starter `app/main.py`. "Fixed" always refers to the rewritten `app/main.py`; the test that guards each fix is named where one exists. Example times assume a 09:30-18:30 IST shift.

| # | Where | What is wrong | How you'd notice it | How I fixed it |
|---|---|---|---|---|
| 1 | `compute_late_minutes` | Builds the shift start with `punch_in.replace(hour, minute)` on the punch-in's **own** clock. For a UTC/naive datetime that is not IST, so the shift start is wrong (R1). | Punch in at 10:05 IST (= 04:35 UTC): the start becomes 09:30 *UTC*, the difference is negative, result `0` instead of `35`. | `shift_window()` builds the start as an aware IST datetime from the attendance date. `test_late_is_measured_in_ist_not_utc`. |
| 2 | `compute_late_minutes` | `int(seconds/60) > 10` tests whole minutes, so the "strictly more than 10:00" rule (R2) is off by one second. | 09:40:01 gives `int(10.01)=10`, `10 > 10` is false, returns `0`; the contract says `10`. | Compare in seconds (`> 600`), then floor to minutes. `test_late_minutes`. |
| 3 | `compute_late_minutes` | No overnight handling: the shift start is always on the punch-in's own calendar day. | Shift 22:00-06:00, punch-in 00:30 (belongs to yesterday's shift): start is "today 22:00", in the future, so late = `0` instead of `150`. | The start comes from the **attendance date** (R1 rule), not the punch date. `test_late_for_overnight_shift_punching_in_after_midnight`. |
| 4 | all helpers / `punch_in` | Instants are never truncated to whole seconds (R1). | `punched_at` ending in `...900` ms keeps the fraction, so 09:40:00.900 is treated as 09:40:00.9 and stored with it. | `ms_to_dt` floors to whole seconds; the truncated value is stored and returned. `test_punch_in_truncates_to_whole_seconds`. |
| 5 | `compute_work_hours` | Python `round()` is round-half-to-even on a binary float, not half-up (R4). | 54 s is exactly 0.015 h: starter returns `0.01`, contract says `0.02`. Likewise 30186 s: `8.38` vs `8.39`. | Integer seconds, `Decimal`, `ROUND_HALF_UP`. `test_work_hours_half_up_where_float_rounding_is_wrong` (cases found by brute force). |
| 6 | `compute_overtime` | Subtracts an **aware** IST datetime from `punch_out`, which PyMongo returns **naive** (client is not `tz_aware`). | Any punch-out read back from MongoDB raises `TypeError: can't subtract offset-naive and offset-aware datetimes`, a 500. | Client created with `tz_aware=True`; every datetime in the app is aware UTC. |
| 7 | `compute_overtime` | No 30-minute minimum (R3). | Punch out 18:50: returns `20`, contract says `0`. | Minutes are counted only when `>= 30`. `test_overtime_minutes`. |
| 8 | `compute_overtime` | Shift end is taken on the record's date, never moved to the next day for overnight shifts. | Shift 22:00-06:00, punch-out 06:40 next day: end = "06:00 on the start date", result is about 1480 minutes instead of `40`. | `shift_window()` adds a day when `shift_end <= shift_start`. `test_overtime_overnight_shift_ends_next_day`. |
| 9 | module level | `MongoClient(...)` is not `tz_aware`, so stored UTC instants come back naive and can be mistaken for local time. | Defect 6; also epoch conversion drifts by the server's UTC offset. | `tz_aware=True`, plus `dt_to_ms` treats a stray naive value as UTC. |
| 10 | module level | No indexes at all, not even a unique one; nothing runs at startup. | `explain` shows `COLLSCAN`; duplicates are possible (11, 14, 20). | `ensure_indexes()` in the app lifespan, idempotent, 7 named indexes (see DECISIONS.md). |
| 11 | `health` | Always returns `ok`, never pings MongoDB. | Stop MongoDB: `/health` is still 200, so the grader's readiness poll passes against a dead database. | `client.admin.command("ping")`; any `PyMongoError` gives 503 with a generic message. |
| 12 | `EmployeeIn` | No validation: any `emp_code`, any email, any shift string, `shift_start == shift_end`, impossible `joined_on`, no length limits. | `emp_code: "abc"`, `shift_start: "25:99"`, `joined_on: "2026-02-30"` all return 201. | Pydantic patterns/lengths from the contract, a real-calendar date check, and a cross-field `shift_start != shift_end` check. `test_create_employee_validation` (19 cases). |

## Looked at and decided it was fine

- `load_dotenv()` with its default `override=False`: real environment variables already win over `.env`, which is what the contract asks.
- Pydantic ignoring unknown fields: this is the required "if a client sends a derived field, ignore it" behaviour, so the models keep it (`test_punch_in_ignores_client_supplied_derived_fields`).
- Using `emp_code` (not `_id`) as the identifier in every query: correct per DATA_MODEL.md.
- `doc.pop("_id")` after `insert_one`: needed, because PyMongo adds `_id` to the dict. I kept the idea but build responses explicitly instead.
- Status code `201` on the two create endpoints, and sync `def` handlers: correct; FastAPI runs them in a thread pool, which is fine for PyMongo's blocking driver.
- The default `MONGO_URI` fallback to localhost: acceptable as a development default because the environment variable always takes priority.
